# ClaimOS demo script (10 minutes)

**Audience:** anyone evaluating ClaimOS — a hiring manager, a client, a classroom. **Runtime:** 10 minutes.

**Setup (before the audience arrives):**

1. `docker compose up -d --build` and open http://localhost:3000.
2. Create two logins in `backend/.env` (`DEMO_ADJUSTER_EMAIL`/`DEMO_ADJUSTER_PASSWORD`, `DEMO_CUSTOMER_EMAIL`/`DEMO_CUSTOMER_PASSWORD`) so both roles are ready at startup, or register users with your `INVITE_CODE`.
3. Beats 3 and 4 (live pipeline runs) need a real `ANTHROPIC_API_KEY` in `backend/.env` — with no key the first LLM call fails closed and the claim records the failure (that's Beat 7's failure story, done deterministically, with zero spend). The stack never needs a key to serve, stream, or show traces of an already-processed claim.

Every beat below works on main as written — there are no placeholder demos. The seeded database has 10 policies and 15 historical claims (policy numbers like `AUTO-2024-012001`), so the console is alive on first login.

**Beat 1 — 0:00–0:45 · The glass box.** *(Point at: the dashboard, then the sidebar.)* Say: "This is a claims system where the AI's reasoning is the product. Every claim runs six agents in the open — Intake, Policy, Documents, Fraud, Eligibility, Decision — and a human can read exactly how the machine reached its verdict." Do not demo features yet; make them want the walkthrough.

**Beat 2 — 0:45–2:15 · File a claim, and never lose work.** *(Point at: New Claim, the wizard steps.)* Start typing a seeded policy number — `AUTO-2024-012001` — and the holder's details render from the live lookup: coverage limit, deductible, active status. Say: "The lookup is live, not cached — the system verified the policy before I typed anything else." Fill the incident details; mention validation happens as you leave each field. Then the durability flourish: navigate away mid-wizard, come back, and accept the offered draft — "It saved my work quietly, with the time it was saved. A customer who slams the laptop shut at step three loses nothing." Discard the draft when done and leave the submission for Beat 3.

**Beat 3 — 2:15–3:45 · Watch the pipeline think.** *(Point at: the six stage rows, then the streaming reasoning text, then the durations.)* Submit a real claim — incident type `weather_damage`, $4,500, on `AUTO-2024-012001` (that policy covers weather damage). The board streams six `agent_start`/`agent_complete` pairs in order. Narrate one: "Policy just verified the policy is active and weather damage is covered — you can read its reasoning as it works." Point at the connection chip: "This is a live stream over a durable event log — if I lost the network right now, the page would replay exactly what it missed on reconnect." *(Needs the live API key.)*

**Beat 4 — 3:45–5:15 · Straight-through processing, both sides of the gate.** *(Point at: the finalized claim's status badge, then submit the second one.)* The claim from Beat 3 — low severity, clean eligibility, high confidence — finalized itself: `auto_approved`, full trace attached, no human touched it. Now submit the counter-case on the **same policy**: incident type `accident`, $7,800 — also covered, but "accident" isn't in the low-severity class, so the gate fails and the claim escalates to the workbench. Say: "Same policy, minutes apart. One finalized itself; one went to a human — and you can read exactly which leg of the gate failed, on both." *(Needs the live API key; severity classification is deterministic code, so this beat repeats identically every run.)*

**Beat 5 — 5:15–6:45 · The human override, done right.** *(Point at: the SLA-aging badge, then the empty reason field bouncing, then the audit entry.)* Open the workbench queue — the Beat 4 escalation is waiting, with its SLA clock aging. Open the case, then try an override with the reason blank: the system refuses — "A reason is required to override" — and nothing changes. Now type one and submit: status `overridden`, and the audit history writes who, what changed, and why. Say: "A human can always overrule the machine — with a reason on the record, forever. And the decided claim can't be quietly re-opened: the system bounces that too." *(No key needed — the workbench reads stored traces.)*

**Beat 6 — 6:45–8:15 · The customer's view.** *(Point at: the portal timeline, then the uniform error on a wrong code.)* Grab the access code from the Beat 3 submission's confirmation, open `/status` in a logged-out browser, and enter the claim number with the code — the milestone timeline renders, updating on its own. Enter a wrong code: one uniform error, same as an unknown claim number. Say: "The claimant never wonders, never calls, and the lookup can't leak whether a claim exists — the access code never touches a URL. And the decision letter they download is the same PDF the adjuster signed off on." *(No key needed if you show it with an already-decided claim; the Beat 3 claim qualifies after Beat 3.)*

**Beat 7 — 8:15–10:00 · The numbers close — including the failures.** *(Point at: the ops analytics tiles one by one, each figure read live off the screen.)* Read the ops page from your own run: decision cycle times at p50/p90/p95, the straight-through rate, the fraud flag rate, the decision mix, SLA breaches by severity. Say: "Nothing here is hand-entered — every figure is computed from stored claim timelines." Then the failure story, deterministically and with zero spend: run `docker compose stop worker`, submit a claim, and show it waiting calmly in `pending` — "nothing is lost; the queue is the database." Start the worker again (`docker compose start worker`) and the claim picks up and runs to completion in front of you. Say: "A crashed worker is a paused claim, not a lost one." If you want the loud-failure variant too, restart the stack with no `ANTHROPIC_API_KEY`: the claim ends `failed` with the reason on the record and every completed stage intact. Say: "It fails loudly, tells you which agent and why, and keeps the work. Show me another claims demo that admits its failures this well." Close: "Glass-box AI, human override with an audit trail, and a customer who never has to call."

**Rehearsal notes.**

- Beats 3–4 need a live key; everything else runs on the keyless stack. Rehearse the keyless path too — it is the one that never surprises you in front of an audience.
- Beats 3–4 and 7's failure story are the credibility core — do not skip them to save time.
- All arithmetic on screen is deterministic code (rating, payout, severity, SLA): the same submissions produce the same numbers every time, so you can rehearse exactly what you'll show.
- If you present to engineers: the trace page and the API reference line up one-to-one — the board renders `GET /api/claims/{id}/trace`, the portal renders `POST /api/status/lookup`.
